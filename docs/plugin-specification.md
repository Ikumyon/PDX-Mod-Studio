# Plugin Specification (プラグイン仕様書)

この文書は、PDX-Mod-Studio におけるプラグインの構造、メタデータ、および設定ファイルの書き方を定義する。

## 設計方針

*   **完全なプラグイン駆動**:
    本体は汎用的なエディタエンジンおよび構文・スキーマ検査エンジンとして動作し、特定のゲーム（例: HOI4, CK3等）に依存する知識を一切持たない。
*   **配置ルール**:
    すべてのゲーム固有の文法定義、スキーマ、拡張プログラム等は、必ず `plugins/` 配下にのみ配置して拡張を行う。
*   **マニフェスト唯一の固定知識とファイル名の自由度**:
    本体がプラグインに関して事前に定義している唯一の固定知識（ハードコードされたファイルパス）は、各プラグイン直下の **`plugin_manifest.json` というファイル名のみ**である。
    そのため、`plugin_manifest.json` 以外のすべての設定ファイル名や配置ディレクトリ構造はプラグイン開発者が**自由に決定・命名できる**（例: 文脈定義ファイルも `grammar_modes.toml` という固定名にする必要はなく、`my_custom_modes.toml` のようにしてマニフェストに指定すれば動作する）。それ以外の構文、スキーマ、翻訳辞書等のパスも、すべてマニフェストの記述を起点として連鎖的に動的解決・ロードされる。
*   **厳格なエラー処理**:
    必要なマニフェストファイル、TOML、JSON 等が存在しない場合、コード側で曖昧な補完やフォールバックは行わず、すべてエラー（ロード失敗または診断エラー）として処理する。
*   **プラグイン機能の拡張（複合可能）**:
    プラグインは、「文法（grammar）定義」と「実行プログラム（ロジック）」の2つの拡張機能を提供できる。これらは排他（二者択一）ではなく、**1つのプラグインで両方の機能を同時に持つ「複合プラグイン」として構成することも可能**である。
    *   **文法定義機能**: 構文、型、スキーマ定義によってテキスト検査を宣言的に提供する。自由度を低く保ち、書き方を固定する。
    *   **実行プログラム機能**: `.py` などの実行プログラムを記述し、独自の動作ロジックや高度な拡張を提供する。プログラム実装を前提とする設計。

## プラグインの共通基本仕様

すべてのプラグインに共通する基本的な構造とメタデータの定義。

### ディレクトリ配置
プラグインは `plugins/<プラグインID>/` の配下にのみ配置し、その直下に基本メタデータである `plugin_manifest.json` を必ず配置する。

### plugin_manifest.json
プラグインの基本情報と、どの拡張機能（文法定義／実行プログラム）を有効にするかを定義するメタデータファイル。

```json
{
  "id": "my_plugin",
  "name_key": "my_plugin.name",
  "desc_key": "my_plugin.desc",
  "version": "1.0.0",
  
  // オプション：文法定義機能を提供する場合に記述
  "grammar_modes": "grammar_modes.toml",
  
  // オプション：実行プログラム機能を提供する場合に記述
  "entry_point": "main.py"
}
```

#### 基本必須フィールド
*   **`id`** (文字列, 必須): プラグインを一意に識別するID。ディレクトリ名と一致する必要がある。
*   **`name_key`** (文字列, 必須): UIに表示するプラグイン名の翻訳キー。
*   **`desc_key`** (文字列, 必須): UIに表示するプラグイン説明文の翻訳キー.
*   **`version`** (文字列, 必須): プラグインのバージョン。

#### 機能拡張用のオプションフィールド（複合可能・少なくともどちらか一方は必須）

> [!IMPORTANT]
> 以下のフィールドはオプションですが、プラグインとして動作するためには**少なくともどちらか一方（または両方）が指定されている必要があります**。両方のフィールドが指定されていない（空の）マニフェストファイルは、無効なプラグインとしてロード時にエラーとなります。

*   **`grammar_modes`** (文字列, 任意):
    文法定義機能を提供する場合に、文脈定義ファイル（`grammar_modes.toml`）への相対パスを指定する。これが指定されると、本体は文法エンジンとしてこのプラグインの定義をロードする。
*   **`entry_point`** (文字列, 任意):
    実行プログラム機能を提供する場合に、エントリーポイントとなるスクリプト（例: `main.py`）への相対パスを指定する。これが指定されると、本体は実行エンジンとしてこのプログラムを呼び出す。

## 1. 文法定義機能を追加する場合の書き方

構文や型、スキーマによるテキスト検査を提供する場合の構成方法。

### ディレクトリ構成
文法定義を行う場合、プラグイン配下は以下のようにディレクトリおよびファイルを構成する。

```text
plugins/hoi4/
  plugin_manifest.json       # マニフェスト (grammar_modes を指定)
  grammar_modes.toml        # 文脈ごとのスキーマ適用ルール定義 (必須)
  translations/              # 翻訳辞書
    en-US.json
  grammar/                  # 構文規則・型定義・スキーマ
    syntax.toml
    values.toml
    schemas/
      decision.schema.json
```

### 構成ルール
*   マニフェストファイルで `grammar_modes` に共通の[文脈定義ファイル](./plugins/grammar-modes-toml.md)（例: `grammar_modes.toml`）への相対パスを指定する。
*   共通の[構文解析ルール](./plugins/grammar-syntax-toml.md)（`syntax.toml`）や[型判定パターン](./plugins/grammar-values-toml.md)（`values.toml`）、個別の[スキーマ JSON](./plugins/grammar-schema-json.md) などを `grammar/` ディレクトリ内に配置する。

## 2. 実行プログラム機能を追加する場合の書き方

独自の実行ロジックを提供する場合の構成方法。

### 構成ルール
*   マニフェストファイルで `entry_point` に実行エントリーポイント（例: `main.py`）を指定する。
*   高度な自由度を持つため、プログラムを実行する前提で、プラグインディレクトリ内部に任意のスクリプトや補助プログラムを自由に配置して設計できる。~~みんなも任意のコード実行しよう!~~ プラグインの導入は自己責任です。導入により悪意のあるコードが実行された場合でも、開発者は一切の責任を負いません。
