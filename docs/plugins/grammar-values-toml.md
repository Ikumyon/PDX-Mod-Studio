# 型定義ファイル (Values TOML)

この文書は、テキストから構築された抽象構文木（AST）の各要素（代入の右辺値やブロック内の項目など）が、どのようなデータ型を満たしているかを判定するための**型判定パターン定義ファイル**（例: `values.toml`）の書き方を定義する。

特定のゲームや構文で使われる型情報は本体に埋め込まず、プラグイン側の実ファイルとして配置する。本体の型判定エンジンは、この TOML の設定に従って任意の型名に意味を与え、動的にバリデーションや自動補完を行う。

## ファイル配置

本ファイルの配置場所やファイル名はあらかじめ固定されておらず、**完全に自由**である。
本体（型判定エンジン）は、[文脈定義ファイル (Modes TOML)](./grammar-modes-toml.md) の `[grammar]` テーブルの `values` キーで指定された相対パスから動的に解決して本ファイルをロードする。

典型的な配置例（`grammar_modes.toml` 内で `values = "grammar/values.toml"` と指定した場合）：

```text
plugins/hoi4/
  plugin_manifest.json
  grammar_modes.toml
  grammar/
    values.toml
```

## 最小・完整な構造例

以下は、 Clausewitz 構文やその他のテキストで必要とされる典型的な型（真偽値、整数、浮動小数点数、日付、識別子、列挙型、ブロックなど）を定義する例である。
型名はプラグイン開発者が**自由**に命名して定義することができる。

```toml
[value.boolean]
literals = ["yes", "no"]

[value.string]
pattern = "\"^.*$\""

[value.int]
pattern = "^-?[0-9]+$"

[value.float]
pattern = "^-?[0-9]+(\\.[0-9]+)?$"

[value.date]
pattern = "^[0-9]{4}\\.[0-9]{1,2}\\.[0-9]{1,2}$"

[value.id]
pattern = "^[a-zA-Z0-9_.-]+$"

[value.country_tag]
pattern = "^[A-Z0-9]{3}$"

[value.variable]
pattern = "^[a-zA-Z_][a-zA-Z0-9_]*$"

[value.enum]
literals_from = true

[value.block]
children = true
```

## 設定項目一覧

### `[value.<型名>]`

任意の型名を定義するテーブル。 `<型名>` 部分には、スキーマ定義などで参照したい自由な識別子（例: `int`, `my_custom_type`）を記述する。
テーブル内には、その型をどのように判定するかを規定する以下のキーを記述できる。

*   **`pattern`** (文字列, 任意):
    *   値の文字列が満たすべき規則を定義する正規表現パターン。
    *   値がこのパターンにマッチする場合、その型であると判定される。
*   **`literals`** (文字列の配列, 任意):
    *   型として許容される固定値（リテラル）のリストを指定する。
    *   例: `literals = ["yes", "no"]` と指定すると、値が `"yes"` または `"no"` のいずれかに完全一致する場合のみ判定をパスする。
*   **`literals_from`** (真偽値, 任意):
    *   外部リソースや別の定義（ゲームファイル内のオブジェクト一覧など）から動的にリテラルをロードするかどうか。
    *   `true` を指定した場合、本体のインデックス処理や補完エンジンと連携し、動的なリストをもとに判定が行われる。
    *   明示的に指定しない（キー自体を省略する）場合は `false` として扱われる。
*   **`children`** (真偽値, 任意):
    *   対象の値が単一のリテラルではなく、ブロック構造（子要素や複数のネストされたプロパティ）を持つことを許可するかどうか。
    *   `true` を指定した場合、この型はブロック構造を表す特別な型として認識される。
    *   **重要**: `children = true` が記述されている場合、パーサーは [構文定義ファイル (Syntax TOML)](./grammar-syntax-toml.md) 内の `[syntax.children]`（ブロックの開始/終了記号や区切り方法などの定義）をもとに子要素の解釈を開始する。
    *   明示的に指定しない（キー自体を省略する）場合は `false` として扱われる。

## スキーマ定義 (Schema JSON) との連携

`values.toml` で定義した型名は、[スキーマ定義ファイル (Schema JSON)](./grammar-schema-json.md) の `type` フィールドでそのまま参照される。

### スキーマ側での参照例

```json
{
  "properties": {
    "priority": {
      "type": "int",
      "usage": "optional"
    },
    "tag": {
      "type": "country_tag",
      "usage": "required"
    }
  }
}
```

この例では、`priority` の値が `values.toml` の `[value.int]` で定義された判定ルール（正規表現 `^-?[0-9]+$`）を満たしているか、また `tag` の値が `[value.country_tag]` の判定ルール（正規表現 `^[A-Z0-9]{3}$`）を満たしているかを、本体が自動的に検証する。

## エラーハンドリングと厳格な仕様

本体の型判定およびバリデーションエンジンは、曖昧な補完やフォールバックを行わず、設定ファイルに記述されたルールを厳格に適用する。

1.  **必須ファイルの不在**:
    *   `grammar_modes.toml` で `values` の指定があるにもかかわらず、そのパスにファイルが存在しない場合は、一切の補完を行わず**読み込み時エラー**とする。
2.  **未定義の型名参照**:
    *   Schema JSON 内で `values.toml` に定義されていない型名（例: `"type": "unknown_type"`）が参照された場合、構文解析時に即座にエラーとして扱う。
3.  **キー未指定時のデフォルト挙動**:
    *   `literals_from` や `children` などの真偽値キーが明示的に定義されていない場合は、**すべて `false` 扱い**として処理する。コード側で暗黙の補完や他の型に基づく自動推論は行わない。
