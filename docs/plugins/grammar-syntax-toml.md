# 構文定義ファイル (Syntax TOML)

この文書は、エディタで開いたテキストファイルを抽象構文木（AST）に解析するための構文規則を定義する**構文定義ファイル**（例: `syntax.toml`）の書き方を定義する。

特定のゲームや構文の意味は本体に埋め込まず、プラグイン側の実ファイルとして配置する。本体の構文解析エンジンは、この TOML の設定に従ってテキストをトークン化し、AST を構築する。

## ファイル配置

本ファイルの配置場所やファイル名はあらかじめ固定されておらず、**完全に自由**である。
本体（構文解析エンジン）は、[文脈定義ファイル (Modes TOML)](./grammar-modes-toml.md) の `[grammar]` テーブルの `syntax` キーで指定された相対パスから動的に解決して本ファイルをロードする。

典型的な配置例（`grammar_modes.toml` 内で `syntax = "grammar/syntax.toml"` と指定した場合）：

```text
plugins/hoi4/
  plugin_manifest.json
  grammar_modes.toml
  grammar/
    syntax.toml
```

## 最小・完整な構造例（Clausewitz 構文）

以下は、Clausewitz 構文（`.txt` 形式のスクリプトなど）を解析するための典型的な構文定義ファイルの構成である。

```toml
[syntax]
name = "clausewitz"
assignment = "="
comment = "#"

[syntax.tokens]
string_quote = "\""
escape = "\\"

[syntax.whitespace]
newline_significant = false
indent_significant = false

[syntax.children]
children_by = "delimiter"
open = "{"
close = "}"
```

---

## 設定項目一覧

### `[syntax]`

構文の全体的な基本トークンを定義する。

*   **`name`** (文字列, 必須)
    *   この構文定義の名前。ログや診断で構文を特定するために使用される。
*   **`assignment`** (文字列, 必須)
    *   代入を表す演算子（例: `=`）。左辺と右辺を区切る基準となる。
*   **`comment`** (文字列, 必須)
    *   コメント行または行末コメントの開始文字（例: `#`）。この文字から行末までは解析時に無視される。

### `[syntax.tokens]`

トークン（文字列リテラルなど）の内部表現に関する定義。

*   **`string_quote`** (文字列, 必須)
    *   文字列リテラルを囲むためのクォーテーション文字（例: `"`）。
*   **`escape`** (文字列, 必須)
    *   文字列リテラル内などで特殊文字をエスケープするための文字（例: `\\`）。

### `[syntax.whitespace]`

空白文字や改行の扱いに関する定義。

*   **`newline_significant`** (真偽値, 必須)
    *   改行が構文上の区切り（ステートメントの終了など）として意味を持つかどうか。
    *   `false` の場合、改行は単なるスペースと同様に扱われる。
    *   明示的に指定しない（キー自体を省略する）場合は `false` として扱われる。
*   **`indent_significant`** (真偽値, 必須)
    *   Pythonのようにインデント（行頭のスペース数）がブロックのネスト構造を定義するかどうか。
    *   `false` の場合、インデントは無視される。
    *   明示的に指定しない（キー自体を省略する）場合は `false` として扱われる。

### `[syntax.children]`

ブロック構造（子要素のまとまり）に関する定義。
[型定義ファイル (Values TOML)](./grammar-values-toml.md) にて `children = true` と指定された型を解析する際、このブロック構造ルールをもとに子要素の解釈が開始される。

*   **`children_by`** (文字列, 必須)
    *   ブロック内の子要素をどのように区切るかを規定する。指定可能な値は以下の通り。
        *   **`"delimiter"`**: 明示的な開始記号（`open`）と終了記号（`close`）で囲まれたブロック構造（例: `{ ... }`）。
        *   **`"indent"`**: インデント（行頭のスペースやタブ）の深さの変化によってブロックのネスト構造を表現する方式。
*   **`open`** (文字列, `children_by = "delimiter"` の場合は必須)
    *   ブロック（ネストされたスコープ）の開始を定義する文字（例: `{`）。
*   **`close`** (文字列, `children_by = "delimiter"` の場合は必須)
    *   ブロックの終了を定義する文字（例: `}`）。

## 診断とエラーハンドリング

本体は構文定義ファイルに不備がある場合、以下のように厳格に処理する。

1.  **必須項目の不在**:
    *   指定されたパスに構文定義ファイルが存在しない、あるいは `name` や `assignment` などの必須定義が欠落している場合、パーサーは曖昧なフォールバックを行わず、**読み込み時エラー**とする。
2.  **不整合な構文定義**:
    *   `open` と `close` が同じ文字になっているなど、構文定義に矛盾がある場合はエラーとする。
3.  **キー未指定時のデフォルト挙動**:
    *   `newline_significant` や `indent_significant` などの真偽値キーが明示的に定義されていない場合は、**すべて `false` 扱い**として処理する。
