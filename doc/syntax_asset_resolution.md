# 文法資産解決仕様

本書は、PDX Mod Studio において、各タブやプラグインが外部の文法プラグインをどのように参照するかを定義する。

ここでいう文法プラグインとは、スキーマ、effects、triggers、formatter 定義、診断用ルールなどの文法資産を提供するプラグインを指す。

本書の目的は、文法資産の置き場と利用者を分離し、本体とプラグインの責務境界を明確にすることである。

## 1. 基本方針

- 文法資産の実ファイルはプラグイン資産として扱う
- 文法資産の読み込みと解決は本体が担う
- タブや他プラグインは、本体を通して文法資産を取得する
- タブや他プラグインは、外部プラグインのファイルパスや内部フォルダ構造に依存しない

この方針により、次を両立する。

- 文法だけを持つプラグイン
- 文法とカスタムタブを一体で持つプラグイン
- 文法プラグインと UI プラグインを分離した構成

## 2. 文法資産とは何か

文法資産とは、本体が解釈できる宣言的データを指す。

例:

- スクリプト構文スキーマ
- effects 一覧
- triggers 一覧
- formatter 定義
- validator 定義
- ファイル走査規則
- 診断用補助データ

文法資産は `json`、`toml`、その他のテキスト形式で保持してよい。

ただし、それらをどのように読むかは本体責務であり、利用側プラグインの責務ではない。

## 3. 役割分担

### 3.1 本体

本体は次を担う。

- プラグインの読み込み
- 文法資産の登録
- 文法資産の依存解決
- 文法資産のキャッシュ
- タブやプラグインへの文法資産配布

### 3.2 文法プラグイン

文法プラグインは次を担う。

- 文法資産ファイルの提供
- 自身が公開する文法資産の宣言
- 必要なら他プラグインへの公開単位の定義

文法プラグインは、実行コードを持たなくてもよい。

### 3.3 UI プラグイン / カスタムタブ

UI プラグインやカスタムタブは次を担う。

- 自分が必要とする文法資産の宣言
- 本体経由で取得した文法資産の利用
- 取得した文法資産にもとづく UI 表示や補助機能の実装

UI プラグインやカスタムタブは、外部文法プラグインの実ファイルを直接読んではならない。

## 4. 直接参照を禁止する理由

たとえば `eu4_form` が `plugins/eu4_syntax/...` のような実ファイルパスを直接読めるようにすると、次の問題が起きる。

- フォルダ構造変更に弱い
- 本体のキャッシュや依存解決を通らない
- どの資産が公開対象か曖昧になる
- 一体型プラグインと分離型プラグインで扱いが分かれる
- 将来のローダ変更に弱い

したがって、利用側は「どのファイルを開くか」ではなく、「どの文法資産が必要か」を本体へ要求する。

## 5. 解決モデル

本体は、文法資産をファイルパスではなく論理的な公開資産として扱う。

利用側は次を知っていればよい。

- 必要な資産の種別
- 必要な資産の論理名
- 必要なら依存先プラグイン ID

本体は次を知っている。

- どのプラグインが何を公開しているか
- どのプラグインがどのプラグインへ依存しているか
- 要求された資産をどこから解決すべきか

## 6. 公開資産の考え方

文法資産は、実ファイル名ではなく「公開資産」として扱う。

公開資産とは、他プラグインやタブから参照してよい論理単位である。

例:

- event schema
- achievement schema
- effects list
- triggers list
- decision formatter

重要なのは、公開資産の識別単位が「ファイル名」ではなく「意味単位」であることだ。

これにより、実装側は内部でファイルを分割していてもよいし、逆に複数の定義を 1 ファイルにまとめていてもよい。

## 7. 依存関係

`form` プラグインが外部の `syntax` プラグインを使う場合、依存は明示的に扱う。

例:

- `eu4_form` は `eu4_syntax` に依存する
- `eu4_form` は自分では schema を持たず、`eu4_syntax` が公開する schema を使う

本体は依存解決において次を保証する。

- 依存先プラグインを先に読み込める
- 依存先が無効または欠落している場合、利用側を不完全状態として扱える
- 依存先から読み取れるのは公開資産に限定される

## 8. 一体型プラグインとの整合

このモデルは、文法プラグインと UI プラグインを分ける場合だけでなく、一体型プラグインにも適用する。

たとえば `hoi4` が文法資産とカスタムタブを同じプラグインに持つ場合でも、タブは「自分自身のプラグインが公開する文法資産」を本体経由で取得する。

したがって、本体から見たモデルは次のように統一される。

- 外部依存型
  `eu4_form` が `eu4_syntax` の資産を読む
- 自己完結型
  `hoi4` が自分自身の資産を読む

どちらの場合も、タブはファイルを直接読まず、本体の解決機構を使う。

## 9. 本体キャッシュ

本体は文法資産を都度読み直すのではなく、必要に応じてキャッシュしてよい。

キャッシュ対象の例:

- スキーマの読み込み結果
- effects / triggers の一覧
- formatter 定義
- validator 定義

キャッシュは本体都合で更新してよい。

ただし、利用側へ返す意味内容は、公開仕様として一貫していなければならない。

## 10. 利用側の責務

タブやプラグインは、取得した文法資産を次の用途に使ってよい。

- 入力候補表示
- UI の表示制御
- バリデーション補助
- フォーマット補助
- 新規作成テンプレート補助

一方で、次のことは本体へ委ねる。

- 実ファイル形式の読み込み
- 依存解決
- どの資産が有効かの判定
- 公開対象か内部資産かの判定

## 11. 禁止事項

利用側プラグインやタブは、次を行ってはならない。

- 他プラグインの内部ファイルパスへ依存する
- 他プラグインの内部フォルダ構造を前提にする
- 公開されていない文法資産を直接読む
- 文法資産の再読み込みやキャッシュを本体外で独自に固定化する

## 12. この設計の利点

この方式には次の利点がある。

- 文法だけのプラグインを正式に扱える
- 文法と UI を分離しても密結合になりにくい
- 一体型プラグインとも同じモデルで扱える
- 本体が解析・診断・整形の共通エンジンを持ちやすい
- 将来的なローダ変更や配布形式変更に強い

## 13. 非目標

本書は次を定義しない。

- 公開資産の具体的な manifest 記法
- 本体 API の具体的関数名
- 文法資産ファイルの個別フォーマット詳細
- schema / effect / trigger ごとのデータ構造詳細

これらは別仕様として定義する。
