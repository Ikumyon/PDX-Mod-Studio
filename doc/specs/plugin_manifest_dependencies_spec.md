# プラグインマニフェスト依存仕様

本書は、`plugin_manifest.json` において、プラグイン間依存と文法資産公開をどのように表現するかを定義する。

本書は特に、次の構成を正規に扱うことを目的とする。

- 文法だけを持つプラグイン
- 文法とカスタムタブを一体で持つプラグイン
- 文法プラグインと UI プラグインを分離した構成

例:

- `hoi4`
- `eu4_syntax`
- `eu4_form`

## 1. 基本方針

- 依存関係は manifest で明示する
- 他プラグインから利用可能な文法資産は manifest で公開する
- 利用側プラグインは、依存先プラグインの内部ファイルパスではなく、公開資産を参照する
- 一体型プラグインと分離型プラグインは同じ仕組みで扱う

## 2. 既存キーとの関係

本書は、既存の `plugin_manifest.json` に次の概念を追加する。

- `dependencies`
- `provides`

これらは任意キーである。

ただし、外部文法資産を参照するプラグインは、原則として両者を適切に使う。

## 3. `dependencies`

### 3.1 目的

`dependencies` は、そのプラグインが正常動作するために必要な他プラグインを表す。

### 3.2 役割

本体は `dependencies` をもとに次を判断してよい。

- 読み込み順
- 不足依存の検出
- UI プラグインの有効 / 無効判定
- 資産解決時の探索対象

### 3.3 意味

`eu4_form` が `eu4_syntax` の schema や effects を利用する場合、`eu4_form` は `eu4_syntax` を依存先として宣言する。

一方、一体型プラグインは外部依存がなければ `dependencies` を省略してよい。

### 3.4 記述単位

依存はプラグイン ID 単位で表す。

依存は「ファイル」や「フォルダ」ではなく、「公開されたプラグイン」に対して張る。

## 4. `provides`

### 4.1 目的

`provides` は、そのプラグインが外部へ公開する資産を表す。

ここでいう資産には、特に文法資産を含む。

### 4.2 公開資産の考え方

公開資産は、内部ファイルそのものではなく、他プラグインや本体から参照可能な論理単位として定義する。

例:

- event schema
- achievement schema
- effects list
- triggers list
- formatter
- validator

重要なのは、参照単位が「実ファイル名」ではなく「意味的な公開名」であることだ。

### 4.3 文法資産と公開資産

文法プラグインは、内部では `json` や `toml` を持ってよい。

しかし manifest では、「どのファイルがあるか」よりも、「何を公開するか」を先に表す。

したがって `provides` は、内部レイアウトではなく公開契約として扱う。

## 5. 本体の解釈

本体は manifest の `dependencies` と `provides` を使って次を行う。

1. プラグインの依存関係を解決する
2. 依存先が不足しているプラグインを検出する
3. 各プラグインが公開する資産を登録する
4. タブや他プラグインからの要求に応じて、公開資産を解決する

本体は、利用側が依存先の内部ファイルを直接参照しなくてもよい状態を提供する。

## 6. 利用側プラグインの見え方

利用側プラグインは、次を知っていればよい。

- 自分がどのプラグインに依存しているか
- どの公開資産を必要とするか

利用側プラグインは、次を知る必要がない。

- 依存先プラグインの内部フォルダ構造
- 実際のファイル名
- 資産のキャッシュ方法
- 読み込み順の細部

## 7. 一体型プラグイン

`hoi4` のように、文法資産とカスタムタブを同じプラグインに含める場合でも、`provides` の考え方は適用してよい。

この場合、タブや補助機能は「自分自身のプラグインが公開している資産」を本体経由で解決する。

したがって、本体から見た扱いは次で統一される。

- `dependencies` がある分離型プラグイン
- `dependencies` が空の一体型プラグイン

## 8. 文法専用プラグイン

文法専用プラグインは、実行コードを持たなくてもよい。

この場合、manifest には次の性質がある。

- `entry_point` は不要でありうる
- `dependencies` は必要に応じて持てる
- `provides` は主要な公開情報になる

本体は、このようなプラグインを「無効なプラグイン」ではなく、「データ提供型プラグイン」として扱う。

## 9. UI プラグイン

UI プラグインは、カスタムタブや補助 UI を提供する。

UI プラグインは、必要なら自前で `provides` を持ってよいし、外部の文法プラグインへ依存してもよい。

たとえば `eu4_form` は次のような意味になる。

- 自身は UI を提供する
- 文法資産は `eu4_syntax` に依存する
- 実際に使う schema / effects / triggers は本体経由で解決する

## 10. 依存不足時の扱い

依存先が見つからない、無効化されている、または公開資産が不足している場合、本体は次を行ってよい。

- 利用側プラグインを不完全状態として扱う
- 該当するカスタムタブを無効化する
- 標準テキストエディタへフォールバックする
- 状態バーやログで依存不足を通知する

重要なのは、依存不足時の扱いも本体責務であり、利用側プラグインが内部パス探索で自己回復しないことだ。

## 11. 設計上の禁止事項

manifest に `dependencies` と `provides` を導入した場合、次を避ける。

- 他プラグインの内部フォルダを直接指定して依存を表すこと
- `provides` に内部ファイル名そのものを公開名として露出しすぎること
- 利用側プラグインが `dependencies` を無視して内部ファイルを直接読むこと
- 一体型プラグインだけ特別扱いして別ルートで解決すること

## 12. 推奨される考え方

manifest の読み方は、次のように整理するのが望ましい。

- `dependencies`
  誰に依存するか
- `provides`
  何を公開するか

これにより、プラグイン間の関係は「どこにファイルがあるか」ではなく、「誰が何を提供し、誰が何を必要とするか」で表現される。

## 13. 非目標

本書は次を定義しない。

- `dependencies` の最終的な JSON 詳細構造
- `provides` の最終的な JSON 詳細構造
- 公開資産の完全な種別一覧
- 本体 API の具体名

これらは、将来の公開 API / 公開仕様として別途定義する。
