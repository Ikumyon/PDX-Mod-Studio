# プラグインモデル

本書は、PDX Mod Studio における新しいプラグインの在り方を定義する。

この文書の目的は、プラグインが本体へどのように参加し、どこまで依存してよいかを明確にすることである。

## 1. 基本方針

プラグインは、本体に対して次のことを行える拡張単位として扱う。

- 機能を追加する
- 既存機能の一部に参加する
- 本体が許可した範囲で既定挙動を変更する

ただし、プラグインは本体の内部実装には依存しない。

プラグインが依存してよいものは、次の 3 つに限定する。

- 公開API
- 公開フック
- 公開仕様

この 3 つに含まれないものは、本体内部実装であり、プラグインからの依存対象にしてはならない。

## 2. 公開境界

### 2.1 公開API

公開APIは、プラグインが本体へ要求を送るための入口である。

例:

- メッセージ表示
- タブを開く
- 現在のアクティブタブを取得する
- 現在のタブに属するプラグインを取得する
- 診断プロバイダを登録する

公開APIは、本体がプラグインに対して互換性を意識して提供する面である。

実装上は `core.api` を公開APIの置き場とする。

公開APIの中には、要求APIだけでなく、イベント購読APIも含まれる。

- 要求API
  プラグインが本体へ何かを依頼する入口
- イベント購読API
  プラグインが本体の状態変化を受け取るための入口

たとえば `open_tab()` は要求APIであり、`subscribe_event("file_saved", ...)` はイベント購読APIである。

イベント購読は、個別の `register_*_handler()` ではなく、hook / event モデルとして `subscribe_event(...)` / `emit_event(...)` に統一する。

### 2.2 公開フック

公開フックは、本体がプラグインを呼び出すための入口である。

例:

- `initialize(plugin)`
- カスタムエディタの `setup(widget, file_path, content)`
- カスタムエディタの `widget.set_params(params)`
- `widget.on_save_triggered()`
- `widget.on_save_as_triggered()`
- `widget.on_write_save_plan()`
- 補助UIの `create_assistant_widget(parent)`
- `export_project_data(plugin, context)`
- `import_project_data(plugin, context, data)`

公開フックは、本体が「ここはプラグインが差し込んでよい」と明示した場所である。

公開フックは、役割ごとに保証範囲を持つ。

- `setup(widget, file_path, content)`
  本体は `widget`、対象ファイルパス、初期内容を渡す
- `widget.set_params(params)`
  本体は `notify_editor_ready(tab_id)` 後に `params` を渡しうる
- `create_assistant_widget(parent)`
  本体は補助UIの親 widget を渡す

### 2.3 公開仕様

公開仕様は、本体とプラグインが共有するデータ契約である。

例:

- `save_plan` の辞書構造
- 保存結果の辞書構造
- `open_tab(..., params=...)` に渡す `params`
- プラグインマニフェストの構造

公開仕様は、関数ではなく約束事である。

公開仕様は、必要であれば helper 関数なしでも成立しなければならない。

## 3. プラグインと本体の関係

プラグインは本体の一部ではあるが、本体内部モジュールそのものではない。

本体とプラグインの関係は、次のように保つ。

- 本体は公開境界を定義する
- プラグインは公開境界を通して機能を追加する
- 本体内部実装はプラグインに公開しない
- プラグインは本体内部の都合に合わせて実装しない

この方針により、将来的に次の構成差を吸収しやすくする。

- 本体とプラグインが同一プロセスで動く
- プラグインを個別に `.exe` 化する
- 本体とプラグインの結合方法を将来変更する

ここでいう `.exe` は、単独 IDE アプリケーションを意味しない。

`pdx.exe` を前提として動くプラグイン実体の配置形式として `.exe` を許容しうる、という意味である。

## 3.5 設計ロジック

このモデルは、次の判断ロジックにもとづいている。

### 3.5.1 なぜ公開境界を分けるのか

公開API・公開フック・公開仕様は役割が異なる。

- 公開APIは、プラグインが本体を呼ぶための入口である
- 公開フックは、本体がプラグインを呼ぶための入口である
- 公開仕様は、両者が共有するデータ契約である

この 3 つを混在させると、次の問題が起きやすい。

- 何を呼んでよいか分かりにくくなる
- 何を実装すべきか分かりにくくなる
- 単なる内部helperが公開API化しやすくなる
- 後方互換性の範囲が曖昧になる

### 3.5.2 なぜ本体内部実装を公開しないのか

本体内部実装をプラグインが直接参照すると、次の問題が起きる。

- 本体のリファクタリングがしづらくなる
- プラグインが本体の private な都合に引きずられる
- `.exe` 化やプロセス分離の自由度が下がる
- 実装共有のつもりが、実質的な密結合になる

本体内部は本体の都合で自由に変えられるべきであり、互換性を守る対象は公開境界に限定する。

### 3.5.3 なぜ helper 関数より仕様を優先するのか

helper 関数は便利だが、それ自体が契約ではない。

たとえば保存結果は、`save_success()` のような helper がなくても、仕様どおりの辞書を返せれば成立するべきである。

```python
{"status": "success"}
{"status": "failed", "message": "error"}
{"status": "cancelled"}
```

この方針により、次の利点がある。

- 実装言語や配置の自由度が上がる
- 本体とプラグインの共有実装を減らせる
- helper の有無に依存しない
- 契約の本質が文書として残る

### 3.5.4 なぜ疎結合を重視するのか

プラグインは、本体へ機能追加や挙動変更を行う存在である。

ただし、挙動変更が許されることと、密結合でよいことは同義ではない。

望ましいのは次の形である。

- 本体が差し替え可能ポイントを定義する
- プラグインはそのポイントに参加する
- 本体は内部構造を公開しない

これにより、将来的に次の変化へ対応しやすくなる。

- プラグイン数の増加
- 標準機能の無効化や差し替え
- 読み込み方式の変更
- 本体とプラグインの配布形態の変更

### 3.5.5 API にすべきかの判断基準

新しい機能を追加するときは、まず次の順で判断する。

1. これは本体内部実装か
2. これは公開フックか
3. これは公開仕様か
4. それでも不足するなら公開APIか

次のものは、原則として公開APIにしない。

- 本体内部の実装補助
- UI都合だけの内部配線
- helper があると楽なだけの関数
- 本体とプラグインの共有ルールで十分表現できるもの

公開APIにするのは、プラグイン側から本体へ要求する明確な必要があるものに限定する。

同様に、状態変化通知は個別の `register_*_handler()` を増やさず、hook / event として整理された形へ統一する。

## 4. 許可されること

プラグインは、公開境界の範囲で次のことを行ってよい。

- 新しいエディタを提供する
- 新しい診断やツールを追加する
- 特定ファイルの開き方を変える
- 保存処理へ参加する
- プロジェクト保存へ参加する
- ナビゲーションや補助UIを追加する
- 本体が許可した既定挙動を無効化または置き換える

たとえば、「標準テキストエディタを候補に出さない」のような変更も、本体が差し替え可能ポイントとして公開していれば許可される。

## 5. 禁止事項

プラグインは、次のことを行ってはならない。

- 本体内部モジュールへ直接依存する
- 本体内部変数を書き換える
- 本体内部クラスの private な都合に依存する
- 本体内部 helper を共有ライブラリとして使う
- 公開されていない辞書構造や属性名を前提にする

次のような依存は避ける。

- `core.api` ではない `core.*` への依存
- 本体内 widget 階層の深追い
- 本体だけが知る内部状態への直接アクセス
- ローダ内部の表現 (`plugin.module` など) への依存

## 5.5 実体形式の考え方

プラグインの実体形式は、公開仕様上は固定しない。

想定する形式は次のとおり。

- `.py`
- `.exe`
- native バイナリ (`.dll`, `.pyd`, `.so`, `.dylib`)

一方で、`.c` は直接ロード対象ではなく、native 実体を生成するためのソースとして扱う。

重要なのは、実体形式の違いを本体全体へ漏らさないことである。

実体形式ごとの差は、ローダ内部へ閉じ込める。

本体の他の箇所は、次だけを前提にする。

- プラグインID
- 公開API
- 公開フック
- 公開仕様

## 6. 保存まわりの扱い

保存まわりは、公開APIではなく、主に公開フックと公開仕様で扱う。

具体的には次のように整理する。

- 保存開始の入口は公開フック
- `save_plan` は公開仕様
- 保存結果の辞書も公開仕様
- 本体は返却された結果を解釈する
- プラグインは仕様に従った結果を返す

保存結果は helper 関数に依存せず、仕様どおりの辞書を返せばよい。

例:

```python
{"status": "success", "primary_path": path}
{"status": "failed", "message": "write error"}
{"status": "cancelled"}
```

## 7. 互換性の考え方

本体は、公開API・公開フック・公開仕様に対して互換性を配慮する。

ただし、次のものには互換性義務を持たない。

- 本体内部実装
- 非公開モジュール
- 過去に存在したが公開境界から外したもの

削除や変更の判断基準は次のとおりとする。

- 公開境界に含むなら維持対象
- 本体内部なら自由に変更可能

## 8. 文書の分け方

今後のプラグイン関連文書は、次の 3 系統に分ける。

- 公開API文書
- 公開フック文書
- 公開仕様文書

1つの文書に全てを混在させない。

## 9. 実装例

### 9.1 良い例

- `core.api.open_tab(path, editor_id)` を使う
- `widget.on_save_triggered()` を実装する
- 保存結果を仕様どおりの辞書で返す

### 9.2 良くない例

- 本体内部モジュールを import する
- 本体ウィンドウの内部属性を直接たどって動作を変える
- helper があることを前提にしないと保存結果を返せない

## 10. まとめ

新しいプラグインモデルは、次の一文で要約できる。

プラグインは、本体の内部実装に依存せず、公開API・公開フック・公開仕様を通して本体へ参加する。
